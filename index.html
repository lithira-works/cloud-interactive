Lecture 10 · Cloud Computing

Cloud Migrations 🚚

Think of this lecture as moving house. Your company's IT stuff lives in an old house (on-premise data center). Migration = moving it to a new house (the cloud).

1What is Cloud Migration?

Definition (learn word-for-word) Cloud migration is the movement of a meaningful portion of your organization's existing IT assets to the cloud.

Break the definition into 3 parts:

"Meaningful portion"

Not one tiny file. A real chunk of the IT estate.

"Existing IT assets"

Apps, servers, databases you already have today.

"To the cloud"

From your own data center to AWS / Azure / GCP etc.

This is where individual applications are migrated. Steps in order:

Key ideaValidation = proving the app works correctly in the cloud before you switch everyone over.

  • It can be considered an evergreen set of people, process and technology that constantly improves as you migrate more applications.
  • Use the first set of application migrations to build the foundation of the modern operating model, and improve it continuously.

Lecture 11 · Cloud Computing

Cloud Native Applications 🧩

How apps are built for the cloud. Story line: Monolith (one big block) → Microservices (Lego bricks) → Cloud native rules (12-factor) → tools and practices (DevOps, CI/CD) → modernizing old apps.

1Monolithic Architecture

The traditional way of building applications. Built as a single and indivisible unit — like a cake baked in one piece. Usually contains:

UI A client-side UI
APP A server-side application
DB A database
MW A middleware

✅ Strengths

  • Less cross-cutting concerns (functions like logging, caching, monitoring are handled in one place)
  • Easier debugging and testing
  • Simple to deploy
  • Simple to develop

❌ Weaknesses

  • Too complex to understand (as it grows)
  • Challenging to make changes
  • Cannot scale components independently
  • Difficult to apply new technologies / features
What is a "cross-cutting concern"?A job that every part of the app needs — logging, caching, monitoring. In a monolith it's one app, so you set it up once.

2Microservices Architecture

  • Breaks an application into a collection of smaller independent units (microservices).
  • These units carry out every application process as a separate service.
  • Built as independently deployable modules.
  • Communicate with each other through pre-defined methods / APIs.
  • Each service can be updated and scaled independently.

✅ Strengths

  • Independent components
  • Easier understanding
  • Better scalability
  • Flexibility in choosing the technology
  • Higher level of agility

❌ Weaknesses

  • Extra complexity of a distributed system
  • Cross-cutting concerns
  • Harder to debug and test
Memory hook: they are mirror images! Monolith's strengths (easy debug/test, few cross-cutting concerns) = Microservices' weaknesses. Monolith's weaknesses (hard to scale, hard to change, no new tech) = Microservices' strengths.

3🎮 How each one scales

Imagine traffic spikes on the Orders feature only. Press the buttons to scale.

Monolithic approach

Contains domain-specific functionality, normally divided by functional layers (web, business, data). Scales by cloning the whole app on multiple servers/VMs/containers.

Microservices approach

Separates functionality into smaller services. Scales out by deploying each service independently, creating instances across servers/VMs/containers.

Exam tipMonolith = clone the whole app. Microservices = scale out only the service that needs it. That's the reason microservices waste fewer resources.

8CI / CD

CI — Continuous Integration

  • The practice of automating the integration of code changes from multiple contributors into a single software project.
  • Developers frequently merge code changes into a central repository where builds and tests then run.
  • Automated tools assert the new code's correctness before integration.

CD — Continuous Delivery / Deployment

  • A software release process that uses automated testing to validate if changes are correct and stable for immediate autonomous deployment to production.
  • Lets engineering organizations focus on core business needs instead of infrastructure overhead.

🙋 Continuous Delivery

  • Developers review and merge code changes, packaged into an artifact.
  • The package moves to a production environment where it awaits approval to be opened for deployment.

🤖 Continuous Deployment

  • The package is opened and reviewed with a system of automated checks.
  • If checks fail → package rejected.
  • If checks pass → automatically deployed to production.
Exam tip — the ONE differenceContinuous Delivery = a human approves the final release. Continuous Deployment = no human, automated checks decide.
Memory: "Delivery" — like a parcel, someone must sign for it ✍️. "Deployment" — robot does it 🤖.

Outline: Containerization concept → Introduction to Docker (+ commands) → Container orchestration. Big analogy: a shipping container — whatever's inside, every ship, truck and crane handles it the same way.

1Why Containers? — "The Matrix from Hell"

Every app needs Libraries + Dependencies, running on an Operating System, on Hardware Infrastructure. Now multiply: many apps × many environments (Development, Testing, QA, Staging, Production). Each combination might break. Click the cells:

The solution (slide)Each app keeps its own Libraries + Dependencies inside a container. All containers sit on one Container Platform → Operating System → Hardware. Same container runs the same everywhere.

2What is a Container?

DefinitionA container is a lightweight, self-contained software package that bundles an application's code with all its dependencies (libraries, system settings) into a single unit.
This ensures the app runs consistently across different environments (developer's laptop or cloud server), because it includes everything it needs, without relying on the host's operating system.

Each container has its own isolated Processes, Network and Mounts, but all share the Operating System Kernel via the Container Platform.

4What is Docker?

  • Docker is a tool that lets developers, sys-admins etc. easily deploy applications in a sandbox (called containers) to run on the host OS, i.e. Linux.
  • Written in the Go programming language; uses several Linux kernel features.
  • Uses namespaces to provide the isolated workspace called the container. When you run a container, Docker creates a set of namespaces for it.
  • Namespaces provide a layer of isolation. Each aspect of a container runs in a separate namespace and its access is limited to that namespace.
Memory hook: "Docker GOes into NAMEd rooms" — written in Go, isolates with Namespaces, runs on Linux.
What technology gives a container its isolation?Namespaces (a Linux kernel feature). Docker creates a set of namespaces for every container.

Docker Daemon (dockerd) — the worker / kitchen chef 👨‍🍳

  • Listens for Docker API requests and manages Docker objects: images, containers, networks, volumes.
  • A daemon can also communicate with other daemons to manage Docker services.

Docker Client (docker) — the waiter 🧑‍🍽

  • The primary way many users interact with Docker.
  • When you type commands like docker run, the client sends them to dockerd, which carries them out.
  • The docker command uses the Docker API. One client can talk to more than one daemon.
Memory hookRestaurant: you (user) tell the waiter (client), waiter tells the chef (daemon), chef gets ingredients from the supermarket (registry).

Docker Image — the recipe / blueprint 📜

  • A read-only template with instructions for creating a Docker container.
  • Often based on another image with customization. E.g. based on ubuntu, but installs Apache web server, your app and config.
  • Defines how a container should be created, which software runs and how it's configured.

Dockerfile — the recipe written down ✍

  • A simple text file with a list of commands the Docker client calls while creating an image.
  • A simple way to automate the image creation process.
  • Commands are almost identical to their Linux equivalents.

Docker Container — the running thing 🏃

A runnable instance of an image. Packages code with all dependencies and runs it in an isolated environment. You can create, start, stop, move, or delete it using the Docker API or CLI, connect it to networks, attach storage, or create a new image from its current state.

Created when a Docker Image is executed.
Runs as an isolated process, but shares the host's OS kernel.
Multiple containers can run on the same system without interfering.
ExampleAn image of Ubuntu OS with NGINX server → docker run → a container where NGINX is running on Ubuntu.

Docker Registry & Docker Hub — the supermarket 🏪

Registry = centralized storage and distribution system for images. Users store, manage and share container images.

  • Docker Hub: the default, most widely used public registry. Docker looks there by default. You can also run your own private registry.
  • Cloud provider registries: Amazon Elastic Container Registry (ECR), Azure Container Registry, Google Container Registry.

Docker Hub details

  • Cloud-based repository service — people push images to it and pull images from it anytime, anywhere via the internet.
  • Makes it easy to find and reuse images; push images as private or public.
  • Mainly used by DevOps teams. Open-source, freely available for all OSs. Like storage: store images, pull when needed.
  • To push/pull you need basic knowledge of Docker.

6Docker Architecture & How it Works

  • Docker uses a Client-Server architecture.
  • The client talks to the daemon, which does the building, running and distributing of containers.
  • Client and daemon can run on the same system, or the client can connect to a daemon remotely.
  • They communicate using a REST API, over a UNIX socket or a network.

10Container Orchestration

DefinitionContainer orchestration is the process of automating the deployment, management, scaling, and networking of containers throughout their lifecycle, making it possible to deploy software consistently across many different environments at scale.
  • Necessary to manage the complexity of modern large-scale containerized apps by automating deployment, scaling and load balancing → improves agility, resilience, efficiency.
  • Streamlines operations, reduces manual effort and errors, more efficient resource use → cost savings and faster development cycles.
Memory hook: "DMSN" — "Don't Make Ships Nervous" — Deployment, Management, Scaling, Networking.

Why do containers need orchestration?

  • Containers are smaller, more resource-efficient and more portable than VMs. Containerized microservices / serverless functions are the de facto compute units of cloud-native apps.
  • In small numbers containers are easy to manage manually. But at scale (large organizations) that's impossible.
  • A CI/CD or DevOps pipeline is impossible without container orchestration, which automates deploying and running containerized apps.

How does it work?

  • Architecture = running container clusters across multiple machines and environments.
  • Each cluster = a group of nodes (server instances).
  • Worker nodes run containers using container runtimes (e.g. Docker).
  • A group of control plane nodes act as the orchestrator of the cluster.
  • Users manage and monitor workloads with tools featuring APIs and GUIs.

Essentially a 3-step process (or cycle): Provisioning → Deployment → Lifecycle management. Memory: "PDL" — "Please Deploy Later".

One-Page Cheat Sheet 📄

Everything that gets asked, on one page. Print it (Ctrl+P) if you like.

L10 · Definition & Process

  • Migration = movement of a meaningful portion of existing IT assets to cloud
  • Process: Opportunity Evaluation → Portfolio Discovery & Planning → App Design ⇄ Migration & Validation → Operate
  • Drivers: hardware renewal, DC lease expiry, productivity, global expansion, M&A, standardized architectures
  • Discovery tools: AWS Discovery Service, Azure Migrate, 3rd party
  • Least complex apps first · parallel envs · partial switch · full cutover
  • Operate: DevOps, NoOps, FinOps, SecOps · evergreen model

L10 · Strategies

  • Gartner 5: Rehost, Refactor, Revise, Rebuild, Replace
  • Azure 4: Rehost, Refactor, Re-architect, Rebuild
  • AWS 6: Rehost, Re-platform, Repurchase, Refactor/Re-architect, Retire, Retain
  • Rehost = lift-and-shift, no code change
  • Re-platform = lift-tinker-and-shift (VM→PaaS, Oracle→PostgreSQL, WebLogic→Tomcat)
  • Repurchase = to SaaS (Salesforce, Workday, SharePoint)
  • Refactor = cloud-native redesign, most expensive
  • Retire = turn off · Retain = later/do nothing
  • Challenges: Cost · Resistance · Skills shortage

L11 · Architecture

  • Monolith: single indivisible unit (UI, server app, DB, middleware). Easy to debug/deploy; hard to scale/change
  • Microservices: small independent deployable services via APIs. Scalable, flexible tech; complex, hard to debug
  • Monolith scales by cloning whole app; microservices scale each service
  • Cloud native: exploits flexibility, scalability, resilience · born in cloud: Netflix, Spotify, Uber, Airbnb · CNCF = containerization focus

L11 · 12-Factor (Heroku)

  • Codebase · Dependencies · Config · Backing services · Build-release-run · Processes · Port binding · Concurrency · Disposability · Dev/prod parity · Logs · Admin processes
  • "Cool Dogs Can Bark But Puppies Play Constantly, Don't Disturb Lazy Adults"

L11 · Tools & Practices

  • Tools: Cloud delivery model, Containers, Microservices, Service mesh, Orchestration
  • Practices: DevOps, SRE (Google), NoOps, CI, CD
  • CI: merge often into central repo, automated build+test
  • Continuous Delivery = human approval · Continuous Deployment = fully automatic
  • Tools: Jenkins, GitLab, GitHub, Bitbucket, CircleCI, TeamCity, Bamboo, Travis CI
  • Modernization: Rehost → Refactor → Rearchitect ×2 → Rearchitect/Rebuild

L12 · Containers & Docker

  • Container: lightweight self-contained package of code + dependencies; consistent everywhere
  • VM: Guest OS + Hypervisor · Container: shares kernel + Container Engine
  • Docker: Go language, Linux kernel features, namespaces for isolation
  • Components: Software (dockerd, docker) · Objects (Image, Container) · Registry
  • Image = read-only template (blueprint) · Container = running instance
  • Dockerfile → build → Image → run → Container
  • Client-server, REST API over UNIX socket or network
  • Advantages: Portability, Consistency, Lightweight, Scalability, Efficiency

L12 · Commands & Signals

  • run = pull + create + start
  • ps = running · ps -a = all · images = local images
  • logs, attach, exec -it
  • stop → SIGTERM · kill → SIGKILL · pause → SIGSTOP · unpause → SIGCONT
  • rm (container) · system prune (all stopped) · rmi (image)

L12 · Orchestration

  • Automates deployment, management, scaling, networking
  • Clusters of nodes · worker nodes run containers · control plane = orchestrator
  • 3 steps: Provisioning → Deployment → Lifecycle management
  • Config file in YAML or JSON
  • Advantages: automation, reliability, resource efficiency, security/portability, modern dev support
  • Tools: Kubernetes, Mesos, OpenShift, ECS, EKS, GKE, Mirantis, Docker Swarm
